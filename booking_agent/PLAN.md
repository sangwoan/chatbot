# 예약/티켓팅 모니터링 에이전트 — 개발 플랜

## 0. 목표와 원칙

**목표**: 품절된 예약(식당·공연·호텔·항공 등)을 24시간 모니터링하다가, 취소표가 나와서 사용자가 정한 기준에 맞으면 자동으로 예약하거나(허용되는 경우) 즉시 알림을 보낸다.

**절대 원칙**
1. **확정 직전 재검증**: 결제/확정 버튼을 누르기 직전에 체크아웃 화면의 실제 값(날짜·시간·인원·금액·취소규정)을 다시 읽고 기준과 대조한다. 탐지 시점 데이터는 신뢰하지 않는다.
2. **결재 게이트**: 아래 중 하나라도 해당하면 자동 확정 금지 → 사용자 승인 요청.
   - 총 결제액 ≥ 100,000원 (외화는 당일 환율로 원화 환산)
   - 취소 수수료 > 예약금의 10%
   - 금액 또는 취소규정을 **파싱하지 못했거나 불확실**한 경우 (fail-closed)
   - 예약금 0원인데 노쇼/취소 수수료가 있는 경우 (비율 계산 불가 → 승인)
3. **이중 예약 방지**: 감시 항목 1개당 확정은 최대 1건. 확정 후 해당 감시 자동 종료.
4. **우회 금지**: CAPTCHA 풀이, 봇 탐지 회피(핑거프린트 위장, 프록시 로테이션 등), 대기열 우회는 구현하지 않는다. 이런 방어가 있는 곳은 **알림 전용**으로 처리한다.
5. **허용 판정 (사용자 결정 2026-10-19)**: 불법이 아니고 사이트 정책에 **명시적 금지**가 없으면 감시를 허용한다. 자세한 기준과 구현은 §9.

## 1. 현실 체크 (리스크)

| 항목 | 내용 | 대응 |
|---|---|---|
| 약관 | 캐치테이블·테이블링·OpenTable·Resy·Tock·인터파크·항공사 등 대부분 자동화 접근을 약관으로 금지. 위반 시 계정 정지 가능 | 플랫폼별로 "모니터만 / 자동예약 / 알림만" 등급을 정하고, 공식 API·제휴 알림 기능이 있으면 우선 사용 |
| 법 | 한국 공연법·국민체육진흥법 개정(2024)으로 매크로를 이용한 입장권 **부정판매(재판매) 목적** 구매는 처벌 대상. 개인 사용 목적이라도 공연/스포츠 티켓은 자동 구매하지 않는 것을 권장 | 공연·스포츠 티켓 = 알림 전용 |
| 속도 | 인기 취소표는 수초~수분 내 소진. 승인 대기 중 사라질 수 있음 | 승인 요청에 타임아웃(예: 3분) + 원탭 승인 버튼. 플랫폼이 "임시 홀드"를 주면 홀드 후 승인 |
| 부하 | 과도한 폴링은 IP 차단·민폐 | 대상별 최소 간격(기본 1~5분) + 랜덤 지터, 동시 접속 1개 |
| 결제정보 | 카드정보 저장은 유출 리스크 | 카드번호 직접 저장 금지. 플랫폼에 저장된 결제수단/간편결제만 사용, 로그인 세션은 암호화 저장 |

> 법률 판단은 전문가 의견이 아니며, 실제 운영 전 각 플랫폼 약관 확인 필요.

## 2. 아키텍처

```
[Watch 설정(YAML/텔레그램 명령)]
          │
   ┌──────▼──────┐   주기 실행(지터)
   │  Scheduler  │──────────────┐
   └──────┬──────┘              │
          ▼                     │
   ┌─────────────┐  플랫폼별 어댑터 (monitor / book / notify_only)
   │  Adapters   │  - 공식 API 우선, 없으면 Playwright 헤드리스
   └──────┬──────┘
          ▼ 후보 슬롯
   ┌─────────────┐  순수 함수: 날짜·시간대·인원·가격·취소규정·우선순위
   │ Criteria    │
   │ Engine      │
   └──────┬──────┘
          ▼ 통과
   ┌─────────────┐  10만원 / 취소수수료 10% / 불확실 → 승인 필요
   │ Policy Gate │──── 승인 필요 ──► [Telegram 승인 요청: ✅ / ❌, 타임아웃]
   └──────┬──────┘
          ▼ 자동 허용 (또는 승인됨)
   ┌─────────────┐  체크아웃 화면 재스크래핑 → 기준·게이트 재평가
   │ Re-verify   │──── 불일치 ──► 중단 + 알림
   └──────┬──────┘
          ▼
   [확정] → 확인번호/확인메일 검증 → 알림 → Watch 종료
          │
   [감사 로그(SQLite): 탐지·판단 근거·스크린샷·결과]
```

### 핵심 데이터 모델 (Watch)
```yaml
id: sushi-omakase-nov
platform: catchtable          # 어댑터 키
target: "가게/상품 URL 또는 ID"
mode: auto_book | notify_only
dates: ["2026-11-07", "2026-11-08"]   # 또는 범위 + 요일 필터
time_window: ["18:00", "20:30"]
party_size: 2
max_total_krw: 300000
currency: KRW
max_cancel_fee_ratio: 0.10
priority: ["2026-11-07 19:00", "*"]   # 선호 순서
poll_interval_sec: 120
expires_at: "2026-11-06T23:59"
```

### 취소 수수료 판정 규칙 (기본값 — 확인 필요)
- 취소규정이 시점별로 다르면(예: 7일 전 무료, 1일 전 50%) **가장 불리한 구간**으로 판정 (보수적).
- 예약금이 없고 전액 현장결제인 경우: 기준 = 예상 총액.
- 규정 텍스트는 LLM으로 구조화 추출하되, **최종 판정은 결정론적 코드**로. 추출 신뢰도가 낮으면 승인 요청.

## 3. 기술 스택

| 영역 | 선택 | 이유 |
|---|---|---|
| 언어 | Python 3.12 | 사용자 친숙(트레이딩 봇) |
| 브라우저 | Playwright | 로그인 세션 유지, 동적 페이지 |
| 스케줄 | APScheduler (asyncio) | 대상별 간격·지터 |
| 저장 | SQLite | 감시·이벤트·감사 로그 |
| 알림/승인 | Telegram Bot (inline 버튼) | 무료, 즉시성, 원탭 승인. 보조: 이메일 |
| 정책 파싱 | Claude API (구조화 출력) | 취소규정/금액 텍스트 추출. 판정은 코드 |
| 환율 | 무료 FX API, 1일 캐시 | 외화 10만원 환산 |
| 호스팅 | 상시 구동 VPS(월 $5~10) 또는 집 PC/NAS | 24시간 필요. 이 클라우드 세션 컨테이너는 휘발성이라 운영 불가 |

## 9. 다중 사이트 감시 설계 (2026-10-19)

### 9.1 허용 판정 기준 (원칙 5)
| 상황 | 판정 |
|---|---|
| robots.txt가 그 경로를 Disallow (`*` 또는 `booking-agent` 그룹) | 금지 — 기계가 읽는 명시적 정책 |
| 약관에 자동화·스크레이핑·로봇 접근 금지 조항 | 금지 |
| 약관이 '서버 부하·운영 방해'를 일으키는 자동 접속만 금지 | 허용 — 60초 이상 간격 유지 |
| 관련 조항 없음 | 허용 |
| 약관 미확인 | 감시 시작 안 함 → 온보딩에서 확인 |
| 기술적 차단(401·403·407·451, 챌린지·CAPTCHA 화면, robots.txt 401·403, 429 3회 연속) | 그 호스트 즉시 중단, 자동 재시도 없음 |

정책과 상관없이 하지 않는 것(원칙 4): CAPTCHA 풀이, UA·핑거프린트 위장, 스텔스 플러그인, 프록시 로테이션, 대기열 우회, 자동 로그인, 차단된 뒤 재시도.
감시는 알림 전용이 기본이다. 자동 예약은 원칙 1~3과 결재 게이트를 그대로 따른다.

### 9.2 구조
```
watch ─▶ 어댑터(http_json · html · nol) ─▶ AccessGate ─▶ 사이트
                                           1) sites 등록부: 약관 판정·차단 기록
                                           2) robots.txt (와일드카드·$·최장 일치, 동률이면 Allow)
                                           3) 호스트별 최소 간격 60초 + Crawl-delay·Retry-After
                                           4) 정직한 UA: booking-agent/1.0
                                           5) 차단 감지 → SiteBlocked → 감시 중단·알림·차단 기록
```
- `agent/access.py`: `AccessGate`, `RobotsRules`, `detect_block`, `SiteBlocked`, `PolicyRefused`
- `agent/adapters/http_json.py`: 공개 JSON 응답 → `watch.options.extract` 규칙으로 슬롯 변환
- `agent/adapters/html.py`: 서버가 그려 주는 HTML → CSS 선택자로 슬롯 변환
- `watches.yaml`의 `sites:` 등록부: 호스트별 `terms`(allowed · load_only · banned · unreviewed), 근거 URL, 확인일
- Store `blocked_hosts`: 실행 중 차단된 호스트. `--unblock HOST`는 사용자가 정책 변경을 확인한 뒤에만 쓴다

### 9.3 새 사이트 온보딩
1. `python -m agent.runner --check-url URL` → 등록부·robots.txt 판정과 Crawl-delay 확인
2. 약관을 읽고 `sites:`에 판정·근거 URL·확인일 기록. 명시적 금지면 여기서 중단
3. 공식 알림·대기·API가 있으면 그것을 먼저 안내
4. 데이터 위치 파악: 페이지가 불러오는 공개 JSON 또는 HTML (1회성, 정직한 UA)
5. `watches.yaml`에 http_json·html 규칙 작성 → `--probe` 결과를 실제 화면과 대조
6. `pytest` 통과 후 커밋, `bash scripts/service.sh restart`
